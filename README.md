# README
## Локальный запуск
Необходимо поставить в IDE плагин для работы с devcontainers, подробнее [здесь](https://containers.dev/supporting). Помимо этого необходимо, чтобы на устройстве были установлены Docker и Docker Compose.

Если IDE не имеет такого плагина, то используем devcontainers-cli, как его ставить смотрим [здесь](https://github.com/devcontainers/cli). Для сборки проекта вводим в директории проекта:
```bash
devcontainer up
```
Для доступа в терминал контейнера вводим:
```bash
devcontainer exec bash
```

После развертывания приложения в контейнере подготавливаем базу данных:
```bash
bundle exec rails db:prepare
```

### Запуск приложения
```bash
bundle exec rails server
```
### Запуск тестов
```bash
bundle exec rspec
```
### Генерация openapi-схемы
```bash
OPENAPI=1 bundle exec rspec spec/requests
```
### Прогонка миграций БД
```bash
bundle exec rails db:migrate
```
## Запуск в production
```bash
RAILS_MASTER_KEY=$(cat config/master.key) MIS_DATABASE_PASSWORD=postgres docker compose up -d --build
```


## Проектирование
Scheduled_at - это время в которое надо начать выполнять задачу, не крайний срок. В описании не было четкого определения что должно быть в этом поле, на макете выглядело так, будто это именно время начало выполннения задачи, что и повлияло на окончательное решение.

Периодические задачи. Для них используется шаблон TaskTemplate, в котором хранятся все данные о задачи. При создании этого шаблона задачи генерируются только на текущий месяц, далее задачи генерируются в начале каждого месяца. Исключение составляет случай, когда предоставлены конкретные даты для задач, здесь генерация происходит один раз. Такая структура решает 3 проблемы:
1. Проблема бесконечности. Задачи генерируются только на текущий месяц, база данных не будет переполнена задачами, которые в ближайшее время неважны.
2. Состояние конкретного экземпляра. Так как периодические задачи генерируются по шаблону, то каждая такая задача будет отдельной записью в базе данных со своим состоянием, независимым от других похожих задач.
3. Исключения из правил. Здесь также - каждая задача имеет свое независимое состояние, а значит сотрудник может ее отредактировать, не затрагивая другие задачи.

Другие крайние случаи:
1. Удаление периодической задачи (в нашем случае её шаблона) - все задачи, дата выполнения которых меньше текущей даты остаются неизменны, у них просто пропадает связь с шаблоном, остальные задачи отменяются.
2. Обновление даты выполнения периодической задачи - здесь проверяется не превыщает ли новое значение время выполнения у ближайшей будущей периодической задачи, сделанной по тому же шаблону.
